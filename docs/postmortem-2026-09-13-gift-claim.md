# 复盘：派猫「领礼物」静默失败（2026-09-13）

> 状态：已修复（commit `4c3bb88`）。本文留作参考，说明这类"看起来成功了其实没有"的自动化故障是怎么产生、又该怎么防。

## 一、现象

每日自动化跑完，报告长这样：

```
签到：今日已签到
派猫：异常（catTravel=unknown-state:领取礼物，已领回流礼物奖励但未进入派遣流程）
```

矛盾点在于：**note 说"已领回流礼物奖励"，状态却卡在「领取礼物」**。礼物到底领没领？答案是没有。

## 二、根因

`wb_auto_task.js` 里领礼物那一段原本是这样的：

```js
await btn.click({ timeout: 6000 });        // 开礼物弹窗
await sleep(2000);
const claim = page.locator(...).filter({ hasText: /领取\s*\d+\s*积分/ }).first();
if (await claim.count()) await claim.click({ timeout: 4000 }).catch(() => {});
await sleep(1500);
await page.keyboard.press('Escape');
await sleep(1000);
await page.goto(GROWTH, ...);              // 刷新回派遣态
```

三个问题叠在一起：

**1. 领取是异步的，被过早的页面刷新打断（主因）**

点「领取 N 积分」后，按钮会变成 **「领取中…」并 disabled**，结算请求还在飞。代码只等 **1.5 秒** 就 `page.goto` 刷新页面 —— 导航会销毁文档，在途请求被直接掐断。礼物没到账，刷新后按钮自然还是「领取礼物」。

实测这次的时间线：

| 时刻 | 按钮状态 |
| --- | --- |
| T + 0.0s | 点下「领取 9 积分」 |
| T + 2.5s | 仍是「领取中…」disabled ← 请求还在飞 |
| T + 3.7s | 才变成「派猫猫旅行」 |

也就是说整个领取要 **2.5–3.7 秒**，而代码只留了 **1.5 秒**。

```
0s        1.5s              2.5s        3.7s
|----------|-----------------|-----------|
           ^ 旧代码在此刷新    ^^^^^^^^^^^ 请求其实还没完成
              → 请求被掐断
```

**2. 全程固定 `sleep`，没有等待条件**

等弹窗 2 秒、等领取按钮 1.5 秒，全靠猜。页面负载一波动，元素晚渲染一点就找不到目标，直接整段跳过。

**3. 空 `catch` 把异常静默吞掉（最坑的一条）**

外层是 `try { ... } catch (e) {}`——异常被吃掉后脚本若无其事地继续往下跑，最后落到 `unknown-state`，**还打上"已领回流礼物奖励"的 note**。故障被伪装成了成功。

## 三、为什么是"最近"才暴露

- **代码一直没变过**。`git show <commit>:wb_auto_task.js` 逐版比对，这段逻辑从首版 `f024c5d`（09-06）到 `b870d99`（09-10）**四个提交字节级完全相同**。这不是回归，是从第一天就存在的竞态。
- **变的是站点侧**。礼物弹窗已从简单的积分弹窗升级成「Buddy 满载而归」富卡片：旅行故事文案 + 研报摘要 + 图片 + 「速看」「快来做同款吧」，点开还要额外拉 `activity/growth/buddy/templates` 和图片资源。弹窗变重 → 结算变慢 → 多出来的 1~2 秒正好把它从"险过"推成"必挂"。
- **之前失败也看不出来**。空 catch + 误导性 note 让它一直报绿。这次只是因为按钮卡在「领取礼物」没进派遣流程，才被状态机逮到。

换句话说：**它很可能已经悄悄失败过好几次了。**

## 四、修复

| 改法 | 说明 |
| --- | --- |
| 引入 `waitUntil(page, fn, timeout, interval)` | 轮询替代固定 `sleep`，等"条件成立"而不是等"时间过去" |
| 领礼物抽成 `claimGift()` | 等 `.gs-modal-overlay` 出现 → 等「领取 N 积分」可点 → 点击 → **等主按钮真正离开「领取」态（最长 20s）** 才算成功 |
| 结果强校验 + 重试 | 没领成功就重试一轮；仍失败则明确报 `gift-claim-failed` 并中止派遣 |
| 异常全部记进 `res.giftLog` | 不再静默吞异常，故障时能直接看到每一步卡在哪 |
| 派遣确认框同样改轮询 | 原来是 `sleep(1500)` 后盲点，现在等确认按钮真的可点 |
| 派遣结果等状态切换 | 等按钮真正切到「旅行倒计时」才判 `dispatched`（最长 20s） |

## 五、验证

```
第 1 次：login:true  catTravel: "dispatched:旅行倒计时 04:00:00"
第 2 次：login:true  catTravel: "already-traveling:旅行倒计时 03:55:57"   ← 幂等，不会重复派遣
```

## 六、可复用的教训

1. **自动化脚本里，`sleep` 是债不是资产。** 凡是"点了之后再操作"，一律轮询等目标出现/可点/状态变更。固定等待在负载波动时必然偶发漏步，而且**失败率会随站点迭代缓慢劣化**，很难归因。

2. **禁止空 `catch`。** `catch (e) {}` 把一个可观测的失败变成了不可观测的伪装成功。至少要写进日志字段（本例的 `res.giftLog`）。

3. **不要相信"动作做过"= "结果达成"。** 点击 ≠ 生效。每一步都要有一个**服务端侧的可验证结果**（本例：按钮文案离开「领取」态）作为成功判据。

4. **状态字段要能自证。** 如果 note 可以声称"已领取"而状态字段仍显示未领取，说明这两个字段没有互相校验。成功判据应该是单一事实来源。

5. **偶发故障先怀疑竞态，再怀疑回归。** 用 `git show <commit>:<file>` 逐版比对能快速排除"是不是改坏了"，把精力集中到环境侧变量上。
