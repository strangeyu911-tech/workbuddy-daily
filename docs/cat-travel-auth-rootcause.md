# 派猫登录态根因（已用 cookie 数据证实）

> 结论先行：「关浏览器/重启都不用重新扫码」是真实存在的，但不是靠 cookie 持久化，
> 而是桌面端**每次打开成长计划时，用自己存的长期令牌换一份新的网站会话**。我们的脚本
> 早期绕开了这步，所以只能靠保活进程，进程一死就要重扫。

## 证据：登录态 = 进程在不在

决定登录状态的是 SSO 会话 cookie。

- 桌面端自己的 Electron profile：`AppData\Roaming\WorkBuddy\Default\Network\Cookies`
  - 会话 cookie → `has_expires=0`、**httpOnly**、secure → **会话级 cookie**，只活在浏览器进程内存里
- 我们自动化的专用 profile：`wb_auto_profile_edge\Default\Network\Cookies`
  - 会话 cookie → 同样 `has_expires=0`、`httpOnly`

会话级 cookie 的特性：**浏览器进程一关就被焚掉**。所以「登录态」本质是「进程在不在」：

- 进程在 → 永不过期（早期连续多天成功，正是因为那个专用 Edge 一直开着没被关）
- 进程没（关窗/重启/崩溃）→ 立刻 `login:false`

这推翻了「cookie 落盘持久」的假设——**两个 profile 的鉴权 cookie 都是会话级，磁盘上没有长期登录态**。

> 识别方法可复用：直接读 Cookies 库的**元数据列**（`has_expires` / `is_httponly` / `expires_utc` / `path`）
> 就够了，这几列本身不加密，无需任何解密或提权，也不必改动浏览器配置。

## 桌面端为什么能免扫码

桌面端持有长期令牌（就是 `workbuddy-desktop.info` 里的 `auth.accessToken`，和每日签到用的是同一个），
打开成长计划时用它在后台**换出一份新的网站会话**（同源 SSO）。
对用户而言这步无感，所以从没看到登录页、也从不扫码；重启电脑后桌面端重新换一次，依旧无感。

## 为什么早期脚本每次重启要扫码

早期版本走的是：专用 Edge profile + 手动扫码登录，**没有接入桌面端自身的会话续期通道**。
所以只能靠「让专用 Edge 一直开着」来保活；一旦关窗/重启，会话随进程消失，下次就只能再扫。

## 修法（已落地 2026-09-15）

不再要求用户扫码：在导航成长中心之前，先用长期令牌换取一份新会话，再 `goto` 目标页
→ 任意重启都自动恢复。

具体实现见 `wb_session_bridge.js`（端点与参数在该文件内部使用，不在文档里重复记录）。
